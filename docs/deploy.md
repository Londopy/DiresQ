# Hosting it

Getting a link you can send somebody. About ten minutes, no card, no cost.

---

## Render, in six steps

1. Sign in at [render.com](https://render.com) with GitHub.
2. **New → Blueprint**, pick the DiresQ repo.
3. It finds `render.yaml` and shows one service, `diresq`. Everything is
   already configured — plan, build command, start command, environment.
4. **Apply**. First build takes three or four minutes.
5. You get `https://diresq.onrender.com` or similar.
6. Open it, sign in as `londo` / `diresq`, check the board is red.

Nothing to configure by hand. `render.yaml` is in the repo, so the deployment
is reviewable like any other file rather than living in somebody's dashboard.

## What the free tier actually gives you

| | |
| --- | --- |
| Memory | 512 MB |
| CPU | 0.1 |
| Hours | 750 per month per workspace |
| Card required | No |
| **Sleeps after** | **15 minutes with no traffic** |
| **Cold start** | **about 60 seconds** |

That cold start is the thing to plan around. A judge clicking your link and
staring at a blank tab for a minute will assume it's broken.

**So say so next to the link.** On both Devposts:

> Live demo: https://diresq.onrender.com — free hosting, so the first load
> takes about a minute while the server wakes up. Sign in as `londo` /
> `diresq`.

And **open it yourself five minutes before judging starts.** It stays awake
for fifteen minutes after any request, which covers a judging window.

Don't rig a cron job to ping it every ten minutes. It burns the 750 hours,
it's against the spirit of a free tier, and it's the kind of thing that gets
noticed.

## The database resets, on purpose

The free tier throws the filesystem away when the instance sleeps, so
`start.sh` runs `init-db` and `seed` on every boot.

That sounds like a limitation and is actually the behaviour you want from a
demo. Every visitor arrives at **the same incident**: eight Katy-area reports,
two hours old, four people converged on a car in a creek, and `s.reyes`
forty-seven minutes out of contact. Nobody lands on whatever the previous
visitor left behind, and nobody sees an empty board.

The seed is written relative to `now`, so it's always freshly two hours old
however long the service has been asleep.

If you ever wanted persistence, it's a Render Postgres instance and a rewrite
of `get_db()`. Not for a demo.

## What's set, and why

| Variable | Value | Why |
| --- | --- | --- |
| `DIRESQ_SECRET_KEY` | generated by Render | Signs session cookies. Unique per service, never in the repo |
| `DIRESQ_HTTPS_ONLY` | `1` | Render terminates TLS, so cookies get marked `Secure` |
| `DIRESQ_DEMO` | `1` | Shows the banner saying it's a demo and the data resets |
| `PYTHON_VERSION` | `3.12.7` | Pinned. "It worked on my machine" is not a deploy strategy |

`DIRESQ_DEV_USER` is **not** set. That's the auth bypass — on a public
instance it would sign every visitor in as the same person.

`DIRESQ_DEMO_SPEED` is **not** set either, which leaves it at 1 and the clock
real. It exists so the silence escalation can be filmed (`docs/filming.md`);
set on a live instance it would make every deadline, countdown and elapsed
time on every page wrong by that factor, while still looking entirely
plausible. It is the one variable here whose misconfiguration is invisible.

## gunicorn, not the dev server

`start.sh` runs gunicorn with two workers and four threads.

The Flask dev server is single-threaded, prints a warning on every boot saying
not to deploy it, and would serve one visitor at a time — which matters here
because the board polls every three seconds and the feed every four.

Two workers on 512 MB is deliberate: the classifier trains at import, so each
worker carries its own copy. Small, but not free. Threads do the rest, because
almost all of the work is waiting on SQLite rather than computing.

## Putting a public disaster app on the internet

Worth thinking about for a minute, because it looks like an emergency service
and isn't one.

**Every page carries a banner** when `DIRESQ_DEMO=1`: this is a demo, nothing
here is real, don't type a real address into it.

**`robots.txt` disallows everything**, so it can't turn up in a search for
someone looking for actual help.

**`/disclaimer` needs no login**, so anybody landing on it can find out what
this is before doing anything.

**Anyone can sign up**, and the data resets anyway. Nothing here is
confidential because nothing here is real.

What we would *not* do is host this somewhere it might be found by somebody in
an actual emergency. A demo link on a Devpost page is fine. A domain called
something like floodhelp.example is not.

## If the build fails

**`ModuleNotFoundError: gunicorn`** — the build command must install both
files: `pip install -r requirements.txt -r requirements-deploy.txt`.

**`Permission denied: ./start.sh`** — the executable bit was lost. Fix with
`git update-index --chmod=+x start.sh`, commit, push.

**Health check failing** — it hits `/disclaimer`, which needs no login. If
that's been changed to require one, the deploy will never go green.

**Blank page, no error** — check the logs for the seed step. If `init-db`
failed the app boots with no tables and every page 500s.

## Other options we looked at

**GitHub Pages** — already used, for the docs site. Static only, so it can't
run Flask.

**Fly.io** — good, but wants a card even on the free allowance.

**PythonAnywhere** — solid for Flask and doesn't sleep, but the free tier is
awkward about outbound requests and the deploy is manual rather than from a
file in the repo.

**Vercel / Netlify** — built for static and serverless JavaScript. Flask can
be forced onto them and shouldn't be.

Render won on: no card, config lives in the repo, deploys from a push, and the
free tier is genuinely free rather than a trial.
